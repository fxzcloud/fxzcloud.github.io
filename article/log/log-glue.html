                                                          # 日志胶水层

                                                          # 概述

                                                          ​

                                                          目标：解决业务系统数据需求的痛点，业务系统仅需要上报自身发生的业务事件，使业务系统从定制化的数据加工中解放出来。

                                                          # 背景

                                                          # 痛点

                                                          常规的服务端埋点方案通常通过日志采集和 binlog 采集相结合的方式实现。binlog 采集主要负责采集表数据，日志采集则作为补充方案，用于弥补底表数据中未覆盖的数据。 在数据指标计算中，常常需要将一个业务事件转化为多个实体维度的数据。业务系统的定制化开发往往导致维护成本高、迭代效率低、业务逻辑与数据加工逻辑紧密耦合，以及数据产出格式不统一等问题。 胶水层负责制定统一的数据格式和规范，作为业务流程中的数据处理节点和数据出口，为关键指标提供底层数据支撑。

                                                          # 期望

                                                          • 业务系统专注于自身发生的事件，无需进行定制化的数据需求开发。
                                                          • 一个业务事件可以被拆解成多个实体事件进行处理。
                                                          • 同一个实体事件可以根据需要进行差异化处理，以适配不同的下游系统或执行不同的逻辑。

                                                          # 设计思路

                                                          # 思路

                                                          1. 业务系统和数据适用方之间引入胶水层，对业务逻辑和数据加工逻辑进行解耦。

                                                          2. 业务系统仅需要关注自身系统所发生的业务事件，按照规范上报业务事件即可，不需要感知数据加工的逻辑。

                                                          3. 胶水层接收业务事件，进行根据准入规则进行准入判断。

                                                          4. 胶水层将业务事件加工为实体事件，可以通过插件的形式，一个业务事件可以产生多个实体事件。

                                                          5. 胶水层通过消费方插件配置将实体事件分发到指定的介质。

                                                          6. 胶水层通过状态对账和补偿尽最大努力保证事件上报、分发的准确性。

                                                            ​

                                                          # 事件

                                                          • 业务事件：单个业务系统中发生的事件，叫业务事件。业务事件可能影响到0个或多个实体。
                                                          • 实体事件：单一实体视角发生的事件，叫实体事件。实体事件只涉及到单个实体，由业务事件加工后得到。

                                                          # 幂等及补偿方案

                                                          业务事件上报后，可能由于网络抖动等原因导致流程中断，从而造成数据丢失或需要进行补偿。在业务系统感知不到上报结果时，可能会有重试的需求。 因此，上报模块需要对业务事件进行幂等处理，即确保同一业务事件只会被处理一次。 同时，在业务事件处理未完成时，如果流程中断，系统应支持重试补偿机制。

                                                          # 幂等方案

                                                          幂等方案设计如下：

                                                          1. 针对不同上游上报的业务事件，生成全局唯一业务事件id。
                                                          2. 在业务事件准入后、将业务事件记录下来，并使用状态机跟踪其处理进度。
                                                          3. 使用全局唯一业务事件id 做幂等处理。

                                                          # 补偿方案

                                                          手动重试： 通过调用接口，传入开始时间和结束时间，扫描该时间段内未完成的任务，并进行重试（重新上报）。 自动重试： 通过定时任务，定期扫描过去某个时间段内未完成的任务，并进行重试（重新上报）。

                                                          # 数据使用方

                                                          当一些下游系统需要使用胶水层的实体事件作为输入以完成自身业务流程时，胶水层可以配置消费插件，将下游所需的数据（实体事件）以下游所需的形式（如 MQ、Hive、HTTP 等）提供给下游使用方。
